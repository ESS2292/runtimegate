setup-python: “Version 3.x was not found in the local cache” and “The version … was not found for Ubuntu”

The “local cache” line is not the error. It is an info message actions/setup-python prints every time a version isn’t preinstalled on the runner. The step fails on the next line, when the version also isn’t in the download manifest for that OS and architecture. Here are five causes, each reproduced, and how to fix each one.

Every log below came from running actions/setup-python v7.1.0 (commit 6d4fd22), using its own dist/setup/index.js, on 23 November 2026. It ran on Node.js 24.22.1 against the live manifest in actions/python-versions (main at 9bc1fe8). The test machine runs Debian 13, and the action chooses builds by Ubuntu release. So for each run, the OS identity was set to Ubuntu 22.04, 24.04, or 26.04 by bind-mounting an os-release file and adding a stand-in lsb_release. Nothing else was changed. These were not GitHub-hosted runner runs, and ::debug:: lines have been removed from the output.

What the two messages mean

In src/find-python.ts, the action first calls tc.find('Python', spec, arch) on the runner’s tool cache. If nothing matches, it logs Version … was not found in the local cache and looks the version up in versions-manifest.json. If the manifest has a build for this OS version and architecture, it downloads it, prints is available for downloading, and the step succeeds. If not, it throws:

Version 3.1 was not found in the local cache
::error::The version '3.1' with architecture 'x64' was not found for Ubuntu 24.04.%0AThe list of all available versions can be found here: https://raw.githubusercontent.com/actions/python-versions/main/versions-manifest.json

(%0A is a newline in a workflow command. The Actions log shows the error as two lines.) So when you see the first line in a passing job, it is harmless. When the job fails, read the version string inside the quotes in the error. It is often not the version you think you asked for.

Cause 1: unquoted 3.10 in YAML becomes 3.1

That '3.1' above came from this workflow:

- uses: actions/setup-python@v7
  with:
    python-version: 3.10

In YAML, unquoted 3.10 is a number, and the number 3.10 is the same as 3.1. To check how GitHub’s own parser handles it, I parsed the workflow with @actions/workflow-parser 0.3.62 (from actions/languageservices, the parser behind GitHub’s Actions language tooling). This matrix and step are the input:

strategy:
  matrix:
    python-version: [3.9, 3.10, "3.10", 3.11]
steps:
  - uses: actions/setup-python@v7
    with:
      python-version: 3.10

The parser returned these tokens:

.jobs.test.strategy.matrix.python-version[0] _NumberToken value= 3.9 toString()= "3.9"
.jobs.test.strategy.matrix.python-version[1] _NumberToken value= 3.1 toString()= "3.1"
.jobs.test.strategy.matrix.python-version[2] _StringToken value= "3.10" toString()= "3.10"
.jobs.test.strategy.matrix.python-version[3] _NumberToken value= 3.11 toString()= "3.11"
.jobs.test.steps[0].with.python-version _StringToken value= "3.1" toString()= "3.1"

The with: value reaches the action as the string "3.1". The generic yaml 2.9.1 package gives the same result ({"python-version":3.1}). The manifest does have a 3.1.4 entry, but it has only Windows files, so on Linux the step fails. A version that isn’t a valid number, such as 3.10.0, stays a string. The same thing happens to any minor version ending in zero (3.20 parses as 3.2).

Fix: quote every version in workflows, including matrix entries: python-version: "3.10". Or better, use python-version-file: .python-version, so the version comes from a plain-text file and YAML never parses it.

Cause 2: the version isn’t built for this runner image

setup-python downloads prebuilt CPython from actions/python-versions, and each build is tied to one Ubuntu release. I counted stable minor versions with a Linux build in the manifest on 23 November 2026:

Ubuntux64arm64
22.043.7 – 3.153.8 – 3.15
24.043.8 – 3.153.8 – 3.15
26.043.10 – 3.153.10 – 3.15

With python-version: '3.7' and Ubuntu 24.04:

Version 3.7 was not found in the local cache
::error::The version '3.7' with architecture 'x64' was not found for Ubuntu 24.04.%0AThe list of all available versions can be found here: https://raw.githubusercontent.com/actions/python-versions/main/versions-manifest.json

The same input with Ubuntu 22.04:

Version 3.7 was not found in the local cache
Version 3.7 is available for downloading
Download from "https://github.com/actions/python-versions/releases/download/3.7.17-5356448435/python-3.7.17-linux-22.04-x64.tar.gz"
...
Successfully set up CPython (3.7.17)

And python-version: '3.9' with Ubuntu 26.04:

::error::The version '3.9' with architecture 'x64' was not found for Ubuntu 26.04.%0AThe list of all available versions can be found here: https://raw.githubusercontent.com/actions/python-versions/main/versions-manifest.json

This matters because of ubuntu-latest. On 23 November 2026, the actions/runner-images README (main at 6d72cf2) maps ubuntu-latest to Ubuntu 24.04 and lists ubuntu-26.04 as a separate label. The README also says -latest labels “point towards the newest stable OS version available” and that migration “happens over 1-2 months.” Based on the manifest above, a job that pins 3.8 or 3.9 on ubuntu-latest will hit this error once that label moves to 26.04. I haven’t seen it happen. That is an inference from the manifest.

Fix: move to a supported Python (3.7, 3.8, and 3.9 are all past end of support). If you really can’t, pin runs-on to an image that still has a build, and treat that as temporary.

Cause 3: an exact patch pin that the newer image doesn’t have

New images only get builds for patch releases made after they arrived. On 23 November 2026, Ubuntu 26.04 x64 had 3.12.13 – 3.12.16 and 3.13.13 – 3.13.18. Ubuntu 24.04 had 3.12.0 – 3.12.16. A .python-version containing 3.12.3 works on 24.04, but on 26.04:

Resolved .python-version as 3.12.3
Version 3.12.3 was not found in the local cache
::error::The version '3.12.3' with architecture 'x64' was not found for Ubuntu 26.04.%0AThe list of all available versions can be found here: https://raw.githubusercontent.com/actions/python-versions/main/versions-manifest.json

When the file said 3.12, the same run resolved to python-3.12.16-linux-26.04-x64.tar.gz and printed Successfully set up CPython (3.12.16).

Fix: pin major.minor in the file CI reads, unless you really need a specific patch. If you do pin a patch, bump it when you change runner images. Make the Dockerfile tag match either way.

Cause 4: the minor version only has pre-releases so far

On 23 November 2026, the only 3.16 entries in the manifest were 3.16.0-alpha.1 and 3.16.0-alpha.2. With python-version: '3.16':

Version 3.16 was not found in the local cache
::error::The version '3.16' with architecture 'x64' was not found for Ubuntu 24.04.%0AThe list of all available versions can be found here: https://raw.githubusercontent.com/actions/python-versions/main/versions-manifest.json

With allow-prereleases: true, the action rewrites 3.16 to the range ~3.16.0-0 (see pythonVersionToSemantic in find-python.ts), and the run succeeds:

Version ~3.16.0-0 was not found in the local cache
Version ~3.16.0-0 is available for downloading
Download from "https://github.com/actions/python-versions/releases/download/3.16.0-alpha.2-42945087804/python-3.16.0-alpha.2-linux-24.04-x64.tar.gz"
...
Successfully set up CPython (3.16.0-alpha.2)

The action.yml description says the input matches prereleases “if no GA versions are found” and that “only ‘x.y’ version range is supported for CPython.” Use it in a matrix entry for early testing. Don’t use it for your production pin.

Cause 5: architecture: x86 on Linux

The manifest’s Linux files are x64 and arm64, plus -freethreaded variants of each. x86 builds exist only for Windows. With python-version: '3.13' and architecture: x86:

::error::The version '3.13' with architecture 'x86' was not found for Ubuntu 24.04.%0AThe list of all available versions can be found here: https://raw.githubusercontent.com/actions/python-versions/main/versions-manifest.json

Fix: remove architecture on Linux. It defaults to the runner’s own architecture (os.arch()).

A checklist when the step fails

  1. Read the version in quotes in the error. If it is 3.1, 3.2, or anything else you didn’t type, it is YAML. Quote the value.
  2. Check runs-on. Find your version and OS release in versions-manifest.json.
  3. If you pinned a patch version, try major.minor, or a patch that has a build for that image.
  4. For a release that isn’t final yet, add allow-prereleases: true, and only in a test matrix.
  5. Remove architecture: x86 on Linux.
  6. Make CI read the same pin as everything else (python-version-file: .python-version), and keep the Dockerfile tag on the same series.

What RuntimeGate catches here, and what it doesn’t

RuntimeGate compares the version declarations in your files with each other. It doesn’t talk to the runner or the manifest. I ran the RuntimeGate 0.2.1 CLI on four small test repos.

Drift (.python-version 3.13, FROM python:3.12-slim, requires-python = ">=3.12", workflow python-version: '3.9'):

RuntimeGate checked 4 declarations (node, python, go, rust).

Errors (2):
  [series-mismatch] Python pins disagree on the major.minor series (3.12 vs 3.13 vs 3.9).
  [range-unsatisfied] actions/setup-python#python-version in .github/workflows/ci.yml (3.9) cannot satisfy pyproject.toml#requires-python ">=3.12" in pyproject.toml.

Warnings (1):
  [hardcoded-ci] Python CI hardcodes a version (actions/setup-python#python-version@.github/workflows/ci.yml:3.9) while a version file is present or referenced. Prefer node-version-file / python-version-file / go-version-file so CI cannot drift.
exit=1

Old pin (everything on 3.7, CI uses python-version-file). A plain check passes because the files agree. With --eol:

RuntimeGate checked 3 declarations (node, python, go, rust).

Errors (2):
  [eol] .python-version in .python-version (3.7) is past end of support (ended 2023-06-27).
  [eol] Dockerfile#FROM in Dockerfile (3.7) is past end of support (ended 2023-06-27).
exit=1

Clean (.python-version 3.13.18, FROM python:3.13.18-slim, requires-python = ">=3.13", python-version-file: .python-version), with and without --eol:

RuntimeGate checked 4 declarations (node, python, go, rust).
OK — declared runtimes agree.
exit=0

Unquoted 3.10 (all files on 3.10, workflow python-version: 3.10 without quotes). This is the case that fails in setup-python:

RuntimeGate checked 4 declarations (node, python, go, rust).

Warnings (1):
  [hardcoded-ci] Python CI hardcodes a version (actions/setup-python#python-version@.github/workflows/ci.yml:3.10) while a version file is present or referenced. Prefer node-version-file / python-version-file / go-version-file so CI cannot drift.
exit=0

Here are the gaps, based on those runs:

  • The YAML 3.10 → 3.1 problem is not detected. RuntimeGate reads the text 3.10, as written, in both with: and a matrix ([3.9, 3.10, 3.11] was read as 3.9, 3.10, 3.11). It only gives the generic hardcoded-ci warning, which doesn’t fail the job. Quoting the value or using python-version-file is the fix.
  • It doesn’t know what each runner image can install. It doesn’t read runs-on or the python-versions manifest. A 3.12.3 pin that is missing on Ubuntu 26.04 passes. --eol does catch 3.7, 3.8, and 3.9, but only because those versions are past end of support, not because of the runner.
  • Pre-release-only versions pass. A .python-version of 3.16 gave no findings, even with --eol.
  • It doesn’t check architecture, allow-prereleases, or check-latest.
  • The free RuntimeGate Lite Action (v1, a30a806) checks Node.js only. On these Python repos it printed RuntimeGate checked 0 declarations (node). and No runtime version declarations found. and exited 0.

RuntimeGate prevents the slower kind of failure: CI, the Dockerfile, and .python-version quietly running different Pythons. It is not a substitute for reading the setup-python error. Checkout for the CLI is not live.
