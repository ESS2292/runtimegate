Guide · November 27, 2026

“error:0308010C:digital envelope routines::unsupported” (ERR_OSSL_EVP_UNSUPPORTED): webpack 4, react-scripts 4, and Node.js version drift

This error usually shows up the day a webpack 4 or Create React App 4 project meets a newer Node.js: a new FROM node: tag, a CI runner moved to a newer Node, or a teammate on a newer laptop install. Node.js 17 and later ship OpenSSL 3, which disables the MD4 hash that webpack 4 uses for module hashes. The usual workaround, NODE_OPTIONS=--openssl-legacy-provider, then breaks the build for anyone still on Node.js 16. Each case below was reproduced, with the fix tested.

All output below came from Docker 26.1.5 on 27 November 2026, using the official images node:16-slim (Node.js 16.20.2, OpenSSL 1.1.1v), node:17-slim (17.9.1, OpenSSL 3.0.3), node:18-slim (18.20.8, OpenSSL 3.0.16), node:20-slim (20.20.2, OpenSSL 3.0.19), node:22-slim (22.23.5, OpenSSL 3.5.9), and node:24-slim (24.22.3, OpenSSL 3.5.9). The test projects are a one-line src/index.js built with webpack --mode production, and a minimal React 17 app built with react-scripts build. Long stack traces and npm notices were trimmed and are marked ....

On Node.js 22.23.5 the same build prints a two-entry opensslErrorStack ('error:03000086:digital envelope routines::initialization error' and 'error:0308010C:digital envelope routines::unsupported') and exits 1. With webpack 5.60.0 and webpack-cli 4.10.0 the first line is [webpack-cli] Error: error:0308010C:digital envelope routines::unsupported, the trace goes through DefinePlugin.js, and the exit code is 2.

The cause is one line. webpack 4.46.0’s lib/util/createHash.js passes the hash name straight to Node: return new BulkUpdateDecorator(require("crypto").createHash(algorithm));, and webpack 4 defaults to md4 (this.set("output.hashFunction", "md4"); in lib/WebpackOptionsDefaulter.js). Calling require("crypto").createHash("md4") directly gives the same result:

node 16.20.2: md4 ok
node 17.9.1:  ERR_OSSL_EVP_UNSUPPORTED error:0308010C:digital envelope routines::unsupported
node 18.20.8: ERR_OSSL_EVP_UNSUPPORTED error:0308010C:digital envelope routines::unsupported
node 20.20.2: ERR_OSSL_EVP_UNSUPPORTED error:0308010C:digital envelope routines::unsupported
node 22.23.5: ERR_OSSL_EVP_UNSUPPORTED error:0308010C:digital envelope routines::unsupported
node 24.22.3: ERR_OSSL_EVP_UNSUPPORTED error:0308010C:digital envelope routines::unsupported

The Node.js 17.0.0 changelog (doc/changelogs/CHANGELOG_V17.md at tag v17.0.0) says so directly: “If you hit an ERR_OSSL_EVP_UNSUPPORTED error in your application with Node.js 17, it’s likely that your application or a module you’re using is attempting to use an algorithm or key size which is no longer allowed by default with OpenSSL 3.0. A command-line option, --openssl-legacy-provider, has been added to revert to the legacy provider as a temporary workaround for these tightened restrictions.”

The exit code is in brackets. The release notes match: webpack v5.61.0 (tag commit 0306510, 29 October 2021) lists “use a wasm md4 implementation for node 17 support”, and v4.47.0 (tag commit dfffd6a, 6 September 2023) lists “[Security] - Add support for md4 in Node >=18” (PR #17628).

The 4.47.0 fix only covers Node.js 18 and later, which explains the Node 17 failure in the table. Its createHash.js sets const NODE_MAJOR_VERSION = parseInt(process.versions.node, 10); and switches to the bundled MD4 only if (NODE_MAJOR_VERSION >= 18). Below 18 it falls through to crypto.createHash(algorithm), which works on Node 16 but not on Node 17’s OpenSSL 3. Node 17 has been end-of-life since 1 June 2022, so that rarely matters now.

Fix 1: upgrade the bundler (tested)

  • Plain webpack 4: move to webpack@4.47.0. It built on Node 18, 20, 22, and 24 with no flags. If package.json says "webpack": "^4.46.0", the lockfile is what holds you on 4.46.0; npm install webpack@4.47.0 updates both.
  • webpack 5: anything from 5.61.0 on. 5.61.0 and 5.113.0 built on every image from Node 16 to 24.
  • Create React App 4: upgrade to react-scripts@5.0.1 (its package.json requires "webpack": "^5.64.4"; it resolved to 5.113.0 here). The test app built on Node 16, 18, 22, and 24.

Overriding webpack inside react-scripts 4 does not work. react-scripts 4.0.3 requires exactly webpack 4.44.2. I added "overrides": { "webpack": "4.47.0" } and reinstalled. npm ls webpack showed 4.47.0 everywhere, but the build stopped at CRA’s preflight check:

There might be a problem with the project dependency tree.
It is likely not a bug in Create React App, but something you need to fix locally.

The react-scripts package provided by Create React App requires a dependency:

  "webpack": "4.44.2"
...
  /app/node_modules/webpack (version: 4.47.0)

With SKIP_PREFLIGHT_CHECK=true it built on Node 16 but still failed on 18, 22, and 24:

Creating an optimized production build...
Failed to compile.

webpack is not the only MD4 user there. The installed babel-loader 8.1.0 has const hash = crypto.createHash("md4"); at line 94 of lib/cache.js. For CRA 4, the real fix is react-scripts 5.

Fix 2: --openssl-legacy-provider, and why it breaks Node.js 16

Setting NODE_OPTIONS=--openssl-legacy-provider made the webpack 4.46.0 build pass on Node 17, 18, 20, 22, and 24 (Version: webpack 4.46.0, exit 0). It also made the react-scripts 4.0.3 build print Compiled successfully. on Node 22. It turns on OpenSSL’s legacy provider for the whole Node process, not just for webpack, and Node’s changelog calls it a “temporary workaround”.

The catch is Node.js 16. On the official node:16-slim image, any build that has the flag set fails before webpack even starts:

$ NODE_OPTIONS=--openssl-legacy-provider npx webpack --mode production
node: --openssl-legacy-provider is not allowed in NODE_OPTIONS
exit=9

$ node --openssl-legacy-provider -p process.version
node: bad option: --openssl-legacy-provider
exit=9

The v16.20.2 doc/api/cli.md explains why: the option was “added: v16.17.0” but only to “Enable OpenSSL 3.0 legacy provider when dynamically linking to OpenSSL 3.x.” The official Node 16 binaries use OpenSSL 1.1.1 (1.1.1v+quic here), so the option does not exist. Exit code 9 is “Invalid Argument: Either an unknown option was specified, or an option requiring a value was provided without a value” (doc/api/process.md at v24.22.1).

This is where version drift comes in. The common hotfix is to bake the flag into the script:

"build": "NODE_OPTIONS=--openssl-legacy-provider webpack --mode production"

With FROM node:22-slim, that repo’s docker build passed. A developer whose .nvmrc still says 16 then runs npm run build and gets:

> wp@1.0.0 build
> NODE_OPTIONS=--openssl-legacy-provider webpack --mode production

node: --openssl-legacy-provider is not allowed in NODE_OPTIONS
exit=9

Without the flag it fails in Docker; with it, it fails on Node 16. Either way, the real problem is that the repo runs two Node.js majors.

How the drift happens

The failing docker build above came from this layout. It builds locally on Node 16 and in CI on Node 16, because setup-node reads .nvmrc:

# .nvmrc
16

# Dockerfile
FROM node:18-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --no-audit --no-fund
COPY src ./src
RUN npm run build

# .github/workflows/ci.yml (excerpt)
      - uses: actions/setup-node@v4
        with:
          node-version-file: .nvmrc

Inside the node:16-slim image the build passed. docker build with FROM node:18-slim failed with the error at the top of this guide. (This used the same commands in containers, not a GitHub-hosted runner.)

A checklist

  1. Pick one Node.js major and use it in .nvmrc, every FROM node:… tag, and CI (node-version-file: .nvmrc).
  2. Upgrade the bundler instead of adding the flag: webpack 4.47.0+ (Node 18+), webpack 5.61.0+, or react-scripts 5.0.1.
  3. If you must use --openssl-legacy-provider, do it only once every pin is on Node 17 or later. Official Node 16 builds exit 9.
  4. Leave Node 16 and 17: both are past end of support.

What RuntimeGate catches here, and what it doesn’t

RuntimeGate compares Node.js pins from .nvmrc, .node-version, .tool-versions, mise.toml, package.json engines/Volta/devEngines, FROM node:…, Compose, dev containers, and actions/setup-node. Node compatibility is the major version. I ran the RuntimeGate 0.2.1 CLI on four small test repos, the same ones built in Docker above.

Here are the gaps, based on those runs:

  • RuntimeGate does not detect this error itself. A “hidden” repo with every pin on Node 22 (.nvmrc, FROM node:22-slim, setup-node) but still on webpack 4.46.0 failed docker build with error:0308010C. The CLI and Lite both printed RuntimeGate checked 3 declarations and OK — declared runtimes agree. and exited 0, and so did --eol. Agreement between pins does not mean your dependencies support that Node version.
  • No dependency or bundler checks. RuntimeGate does not read node_modules, lockfiles, or dependency versions. It cannot tell you that webpack 4.46.0, webpack 5.60.0, react-scripts 4.0.3, or babel-loader 8.1.0 need MD4.
  • NODE_OPTIONS is not read. It does not look at --openssl-legacy-provider in package.json scripts, Dockerfile ENV, or workflow env:. It caught the Node 16 vs 22 split in the flag repo, but not the flag itself.
  • Major version only, with no bundler context. A .nvmrc of 17 next to FROM node:18-slim printed [major-mismatch] Node.js pins disagree on the major version (17 vs 18)., but RuntimeGate does not know that webpack 4.47.0’s fix starts at 18, or that Node 16 rejects the legacy-provider flag.
  • No Docker build-context or runtime awareness. It reads declared pins. It does not build images or run your bundler.

RuntimeGate catches the common root cause, a laptop or CI Node.js major that differs from the image. It is not a substitute for upgrading the bundler. Checkout for the CLI is not live.
