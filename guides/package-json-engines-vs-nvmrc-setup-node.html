When package.json engines, .nvmrc, and setup-node disagree

A version range in package.json, a pin in .nvmrc, and a hardcoded node-version in GitHub Actions are three different declarations. When they drift, installs fail in one environment and pass in another.

Developers run into this as a package-manager error, often far from the file they last edited. A widely cited Stack Overflow thread is titled “The engine ‘node’ is incompatible with this module”: Yarn refused to install because the running Node version was outside a dependency’s engines range. The same error shows up in CI. Another Stack Overflow report failed a GitHub Actions job on Node 18.12.0 when a dependency expected 8 || 10 || 12 || 14 || 16 || 17. A third thread asked how to point nvm at Node 12 after Yarn rejected Node 14 because the project’s own engines field said "node": "12" (question 70841022).

Those three fields are not the same job

npm’s package.json documentation describes engines.node as a range of Node versions the package works on, for example >=0.10.3 <15. Unless the user has set the engine-strict config flag, npm treats that field as advisory and only warns when the package is installed as a dependency. Yarn Classic, by contrast, fails the install with the “engine is incompatible” message above unless you pass --ignore-engines. Ignoring the check hides the mismatch; it does not make the running Node version compatible.

A file such as .nvmrc or .node-version is usually a pin: the exact major, or a full version, that developers and CI should run. engines is usually a range of versions the project claims to support. Those can coexist — the pin should satisfy the range — but they are easy to update independently.

GitHub Actions adds a third copy. actions/setup-node accepts a hardcoded node-version, or a node-version-file pointing at .nvmrc, .node-version, .tool-versions, mise.toml, or package.json. Official docs are explicit: if both inputs are set, node-version wins. A leftover node-version: 20 next to node-version-file: .nvmrc means the next bump of .nvmrc will not change CI.

What setup-node reads from package.json

That file support was requested early. Issue #32, opened 15 August 2019, asked setup-node to understand .nvmrc. Issue #94, opened 12 December 2019, asked it to honor engines. Both are now closed, and the current advanced usage guide documents this lookup order when node-version-file is a package.json:

  1. volta.node, if present
  2. devEngines.runtime for an entry whose name is node
  3. engines.node
  4. The same fields on a file named by volta.extends, recursively

npm’s own docs distinguish engines from devEngines: engines is about the runtime a published package expects, while devEngines is meant to keep people working in the source tree on the same tooling. Pointing CI at package.json is convenient, but a wide range such as ^22 || ^24 is not a pin. setup-node will resolve some version that satisfies the range, and that resolution can move.

A pattern that stays in agreement

Keep one exact pin in .nvmrc (or .node-version). Point Actions at that file, and do not also set node-version. Keep engines.node as a range that the pin satisfies — for example a pin of 22 next to >=22 <23, or a broader range if you genuinely test several majors in a matrix.

- uses: actions/setup-node@v5
  with:
    node-version-file: .nvmrc
    cache: npm

A matrix of Node versions is a valid way to test the range. It is not a substitute for pinning the version that production and the default CI job use. A hardcoded node-version: 20 in one workflow and lts/* in another will drift the next time GitHub’s “current LTS” changes, which is a failure mode Chromatic documented in production.

In a monorepo, a nested package often has its own engines range that is tighter than the root. RuntimeGate scopes each engines field to that package’s directory by default, so a docs/package.json range of >=24 is not compared to a root CI matrix that still includes Node 20. GitHub workflow files belong to the repo root. To compare every range to every pin, pass --engines-scope all or, in RuntimeGate Lite, engines-scope: all.

Then assert the pin and the range still agree

Nothing in setup-node checks that the installed version satisfies engines, or that a Dockerfile FROM node:… line matches .nvmrc. That is a separate consistency check. The free RuntimeGate Lite GitHub Action scans those Node.js declarations and fails the job on a major mismatch, or when a pin cannot satisfy a declared engines range. An optional eol input also fails when a pin is past official end of support, using vendored dates and no network call.

- uses: actions/checkout@v5

- name: Check Node.js version pins
  uses: ESS2292/runtimegate-action@v1
  with:
    eol: "true"
