When go.mod, setup-go, and the Dockerfile disagree

The go line in go.mod is a minimum. A hardcoded go-version, a floating stable tag, or an older FROM golang:… image can still be too old to build the module, and CI that only reads go.mod will not see a stale Dockerfile.

Go’s official toolchain documentation is clear about the go line: it “declares the minimum required Go version for using the module.” A toolchain older than that line refuses to load the module. If automatic toolchain switching is disabled, you get a failure of the form go.mod requires go >= … (running go …; GOTOOLCHAIN=local).

A real Docker build that CI did not catch

That is not hypothetical. On 4 May 2026, stashapp/stash opened issue #6888: make docker-build failed because a backend Dockerfile was still FROM golang:1.24.3 while go.mod declared go 1.25.0. The error was exactly the GOTOOLCHAIN=local message above. The issue is now closed.

The interesting part is why their GitHub Actions job stayed green. The main workflow’s generate job already used actions/setup-go with go-version-file: go.mod, so CI installed a 1.25 toolchain and never exercised the older release-style Docker image. Pointing setup-go at go.mod is the right way to keep CI in lockstep. It does not, by itself, check every FROM golang:… line.

What setup-go reads, and what overrides it

actions/setup-go can take a hardcoded go-version or a go-version-file pointing at go.mod, go.work, .go-version, or .tool-versions. Official docs say that if both inputs are set, go-version wins — the same trap as setup-node and setup-python.

From setup-go v6 onward, a go.mod file is read this way: if a toolchain directive is present, that version is used; otherwise the action falls back to the go directive. The advanced usage guide also notes that a go line with a patch (for example go 1.25.0) installs that patch, while a line without a patch requests the latest available patch of that series.

- uses: actions/setup-go@v6
  with:
    go-version-file: go.mod

A floating value such as go-version: "stable" is a different failure mode. A merged pull request on another project, cozystack/terraform-provider-cozystack#9 (merged 4 June 2026), switched CI from go-version: "stable" to go-version-file: go.mod after the runner’s “stable” toolchain was older than a pending go 1.26.4 directive and failed with GOTOOLCHAIN=local.

Keep the image at least as new as the module

For Docker, the image tag should be at least the major.minor required by the go line — and the same patch, if you need bit-for-bit reproducibility. Official Go images that set GOTOOLCHAIN=local will not quietly download a newer toolchain for you. Prefer bumping FROM golang:… in the same change that bumps go.mod, including Dockerfiles used only for release builds.

Support windows move too. Go’s release policy is that each major release is supported until there are two newer major releases. Go 1.27.0 was released on 19 August 2026, so on that day 1.25 left official support. A repo can have go.mod, CI, and Docker in agreement on 1.25 and still be past end of support.

How to catch this in CI

The free RuntimeGate Lite GitHub Action checks Node.js pins only. If the repository also has a Node frontend or tool version — a setup-node step, a FROM node:… line, or an engines field — add Lite for that subset:

- uses: actions/checkout@v5

- name: Check Node.js version pins
  uses: ESS2292/runtimegate-action@v1
  with:
    eol: "true"

The full RuntimeGate CLI also compares Go pins across go.mod, Dockerfiles, Compose, and setup-go steps, and can optionally fail when a pin is past official end of support using vendored dates (snapshot 10 November 2026). It treats Go compatibility as the major.minor series, and it does not treat a CI matrix as a mismatch against a single Dockerfile. Checkout for the CLI is not live.
