When .tool-versions or mise.toml disagree with .nvmrc, setup-node, and Docker

A team moves to asdf or mise, adds .tool-versions or mise.toml, and leaves the old .nvmrc, the CI step, and the Dockerfile where they were. Each one still installs a version, just not the same one.

The cause is simple: each tool reads only certain files, and it ignores the rest without telling you. Here is what each tool reads, according to its own docs and source. After that come a real drift example and a setup with one source of truth.

Which file each tool actually reads

  • asdf reads .tool-versions: one <tool> <version> per line, with # comments. The Node.js plugin is named nodejs. Extra versions on a line are fallbacks, for example python 3.7.2 2.7.15 system. By default asdf does not read other managers’ files such as .nvmrc; that requires legacy_version_file = yes and a plugin that supports it (asdf configuration).
  • mise reads mise.toml ([tools], for example node = "24") and also reads .tool-versions. If both are in the same directory and both declare a tool, mise.toml wins. mise reads .nvmrc and .python-version (“idiomatic version files”) only for tools listed in idiomatic_version_file_enable_tools, and that list is empty by default (mise version requests and version files, mise.toml reference). So a developer on mise can have a stale .nvmrc in the repo and never install from it.
  • mise version requests are not always exact. node = "24" means a 24.x release, and "lts" and "latest" are aliases that move. mise’s docs say asdf expects exact versions, so a .tool-versions that asdf users also read should hold concrete versions.
  • actions/setup-node reads only the file you give it in node-version-file. Its docs list .nvmrc, .node-version, .tool-versions, and package.json. Support for mise.toml ([tools] node) was added in v7.1.0. Earlier majors don’t list mise.toml in their docs. If node-version and node-version-file are both set, node-version is used (setup-node advanced usage).
  • actions/setup-python takes python-version-file and documents .python-version, pyproject.toml, .tool-versions, and Pipfile. If python-version is also set, the file is ignored (setup-python advanced usage). In its source, any .toml file goes through the pyproject reader, which looks for project.requires-python or Poetry’s Python dependency, not mise’s [tools]. For Python, point it at .tool-versions or .python-version, not mise.toml.
  • Docker reads none of these files. A FROM line can only use ARG values declared before the first FROM (Dockerfile reference), so the image tag is either written out or passed in at build time.

One gotcha: fallback versions in a file CI reads

asdf allows several versions on one line. The CI actions do not parse that format the same way. In setup-node’s source (src/util.ts), a non-JSON, non-TOML file is matched against a pattern that expects an optional node/nodejs name and then a single version on its own line. A line like nodejs 22.11.0 20.18.0 does not match, and the code then falls back to the whole file text. setup-python’s .tool-versions reader also expects python followed by a single version. If CI reads .tool-versions, keep a single version on each line CI depends on.

What drift looks like

Here is a small repo partway through a move to asdf. .tool-versions was updated. .nvmrc, the Dockerfile, and the hardcoded Python version in CI were not:

# .tool-versions
nodejs 22.11.0
python 3.12.1

# .nvmrc
20

# Dockerfile
FROM node:20-alpine

# .github/workflows/ci.yml (steps)
- uses: actions/setup-node@v4
  with:
    node-version-file: .nvmrc
- uses: actions/setup-python@v5
  with:
    python-version: '3.11'

Developers using asdf or mise get Node 22.11.0 and Python 3.12.1. CI and the container get Node 20, and CI gets Python 3.11. Running the RuntimeGate CLI (0.2.1) on that repo printed this and exited 1:

$ runtimegate check .
RuntimeGate checked 6 declarations (node, python, go, rust).

Errors (2):
  [major-mismatch] Node.js pins disagree on the major version (20 vs 22).
  [series-mismatch] Python pins disagree on the major.minor series (3.11 vs 3.12).

Warnings (2):
  [loose-pin] Some Node.js pins are major-only (.nvmrc@.nvmrc:20, Dockerfile#FROM@Dockerfile:20-alpine) while others pin a minor or patch. A major-only tag can float.
  [hardcoded-ci] Python CI hardcodes a version (actions/setup-python#python-version@.github/workflows/ci.yml:3.11) while a version file is present or referenced. Prefer node-version-file / python-version-file / go-version-file so CI cannot drift.

Make one file the source of truth

If the team uses asdf, or uses both asdf and mise, make .tool-versions the source of truth. asdf, mise, setup-node (v4 and later document it), and setup-python (v5 and later document it) can all read it. Delete .nvmrc instead of keeping a second copy. Remember that mise ignores it by default anyway. Point both CI steps at the same file, and pin the Docker image to the same version:

# .tool-versions
nodejs 22.11.0
python 3.12.1

# Dockerfile
FROM node:22.11.0-alpine

# .github/workflows/ci.yml (steps)
- uses: actions/setup-node@v4
  with:
    node-version-file: .tool-versions
- uses: actions/setup-python@v5
  with:
    python-version-file: .tool-versions

Do not also set node-version or python-version in those steps. Both actions let the hardcoded input override the file. With the changes above, the same check printed this and exited 0:

$ runtimegate check .
RuntimeGate checked 5 declarations (node, python, go, rust).
OK — declared runtimes agree.

If the team uses only mise, mise.toml can be the source of truth for Node, as long as CI uses actions/setup-node v7.1.0 or later with node-version-file: mise.toml. setup-python does not read mise’s [tools] table, so keep Python in a file it does read. If a repo has both mise.toml and .tool-versions, mise developers get the mise.toml value, while CI may read the other file. That is drift too. In the fixed repo above, adding a mise.toml with node = "24" made the check fail again:

$ runtimegate check .
RuntimeGate checked 6 declarations (node, python, go, rust).

Errors (1):
  [major-mismatch] Node.js pins disagree on the major version (22 vs 24).

Warnings (1):
  [loose-pin] Some Node.js pins are major-only (mise.toml#tools@mise.toml:24) while others pin a minor or patch. A major-only tag can float.

The Dockerfile still needs a check

Docker can’t read .tool-versions. You can write the tag out, as above, or declare ARG NODE_VERSION before FROM node:${NODE_VERSION}-alpine and pass the value at build time. For example, awk '$1=="nodejs"{print $2}' .tool-versions prints 22.11.0 for the file above, and you can pass that with --build-arg. That moves the problem into your build scripts. A static check also can’t see the final value: RuntimeGate reports an interpolated FROM as a warning (unresolved-interpolation), not as a match. A literal tag plus a CI check that compares it with .tool-versions is easier to verify.

What RuntimeGate reads in these files, and what it doesn’t

  • .tool-versions: lines for node/nodejs, python, go/golang, and rust. It uses only the first version and ignores asdf fallbacks and # comments.
  • mise config: mise.toml, .mise.toml, .config/mise.toml, .config/mise/config.toml, mise/config.toml, and .mise/config.toml, including nested ones. It reads [tools] entries written as node = "24", node = { version = "24" }, a list (the first entry counts), or a [tools.node] table. It does not read mise.local.toml or conf.d fragments. It is a narrow parser, not a full TOML implementation.
  • lts, latest, and system are reported as floating and produce a warning, not a failure. path: and ref: requests produce an “unresolved” warning. For example, node = "lts" next to nodejs 22.11.0 gives a floating-tag warning and exits 0, even though mise resolves lts to a specific major. If you need the gate to fail, pin a number.
  • Node.js pins are compared by major version. Python pins are compared by major.minor series. It compares every file it finds; it does not model mise’s precedence. It records which file node-version-file names, but it does not open that file to confirm what CI will install.
