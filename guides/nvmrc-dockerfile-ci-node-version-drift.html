Do your .nvmrc, Dockerfile, and CI agree on Node.js?

Version files, Docker images, and CI workflows each declare a Node.js version. When they drift, tests can stay green and production can still break.

A Node.js version is often declared in more than one place: a version file such as .nvmrc or .node-version, the engines field in package.json, a FROM node:… line in a Dockerfile, and a node-version input on actions/setup-node. Anyone on the team can update one of those and miss the others.

That is not only messy. It can break production after CI stays green. Chromatic, a development agency, wrote up a real outage: a dependency update passed in GitHub Actions and in a preview environment, then failed in production. Production was on Node 10, the theme’s .nvmrc was 12, and Actions was using the then-current LTS (14). Only production hit the break, because only production was still on 10. In a second project, unpinned Actions started failing when GitHub’s runner images moved to a new LTS.

A similar trap showed up in a merged pull request on Google’s race-condition repo in July 2026: CI was on Node 24, the Dockerfile was on 26, and a Cloud Build step was still on 24. The maintainers added a custom script to assert that those pins agreed, because a pin honored by only one consumer had already caused npm ci failures. See PR #200.

Make one file the source of truth

A practical pattern is: put the exact version in .nvmrc (or .node-version), point GitHub Actions at that file with node-version-file, keep engines as a range that the pin satisfies, and pin the Docker image to the same major (or the same full version if you need a reproducible patch).

- uses: actions/setup-node@v4
  with:
    node-version-file: .nvmrc
    cache: npm

Do not also set node-version in the same step. GitHub’s setup action treats an explicit node-version as the value to install; a hardcoded number next to a version file is how CI drifts again the next time someone bumps only .nvmrc.

Then assert the rest

Dockerfiles and Cloud Build configs usually cannot read .nvmrc on their own. That is why a CI check that compares the declarations — and fails the job when they disagree — is useful. RuntimeGate is one such check: it scans those files and exits 1 on a major mismatch. It is a consistency gate, not proof that production is actually running the pin.

If you only need Node.js in GitHub Actions, RuntimeGate Lite (a free Action, not published yet) covers that subset. The full CLI also checks Python and Go.
