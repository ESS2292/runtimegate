Use a version file in GitHub Actions so CI cannot drift

Point setup-node at .nvmrc (or .node-version) instead of a hardcoded number, then still check Docker and other pins.

actions/setup-node can take a literal node-version, or it can read a file already in the repo. The file form is the one that keeps CI attached to the same pin developers use locally.

- uses: actions/setup-node@v4
  with:
    node-version-file: .nvmrc

The action supports .nvmrc, .node-version, and other files documented by GitHub. If the file is missing, the step fails, which is better than silently falling back to whatever the runner image ships.

Why a hardcoded version is brittle

A workflow that says node-version: "22" will keep installing 22 after .nvmrc is bumped to 24, unless someone remembers the workflow. Chromatic’s write-up (linked in the drift guide) includes the complementary failure: if CI is left on “whatever LTS the runner has,” checks start failing when that LTS changes out from under you.

Prefer the version file as the only number you have to edit. If you also need a compatibility matrix (for example 22 and 24), keep the matrix explicit and make sure each entry still satisfies the range in package.json engines. A matrix is a deliberate set of versions, not a second source of truth for production.

What this does not fix

Pointing Actions at .nvmrc does not update a Dockerfile or a Cloud Build image. Those still have to be pinned separately, and they still need a check so they cannot drift. That is the rest of the job RuntimeGate does: it reads the version file, the workflow, and the Dockerfile in one pass.

Also, a version file is not a substitute for recording end of support. Node 20 reached official end of support on 30 April 2026, according to the Node.js release schedule. A repo can be internally consistent on an unsupported major. An optional --eol check covers that case, using vendored official dates rather than a network call.
