Guide · November 25, 2026

Rust in Docker: “lock file version 4 was found”, “feature edition2024 is required”, and rust-toolchain.toml vs FROM rust:

A Rust project that builds on your laptop can fail in docker build because the FROM rust:… tag is older than the toolchain everything else assumes. Cargo then stops on the lockfile, on a dependency’s edition, or on rust-version. The reverse also happens: if rust-toolchain.toml is copied into the image, rustup quietly downloads that toolchain and the image tag stops mattering. Each case below was reproduced, with the fix tested.

All output below came from Docker 26.1.5 on 25 November 2026, using the official images rust:1.76-slim (cargo 1.76.0, rustup 1.27.0), rust:1.77-slim, rust:1.78-slim, rust:1.85-slim (rustc 1.85.1, rustup 1.28.1), rust:1.95-slim, and rust:1-slim (rustc 1.100.0, rustup 1.29.3). The test crate is a one-file hello binary. Long download, install, and Docker context lines were trimmed and are marked ....

Error 1: “lock file version 4 was found, but this version of Cargo does not understand this lock file”

A Cargo.lock generated by current Cargo (here 1.100.0, no rust-version set) starts with version = 4. Building it with FROM rust:1.76-slim:

> [5/5] RUN cargo build --release --locked:
0.200 error: failed to parse lock file at: /app/Cargo.lock
0.200 
0.200 Caused by:
0.200   lock file version `4` was found, but this version of Cargo does not understand this lock file, perhaps Cargo needs to be updated?
...
ERROR: failed to solve: process "/bin/sh -c cargo build --release --locked" did not complete successfully: exit code: 101

Cargo 1.77.2 printed the same error. Cargo 1.78.0 built the same lockfile without complaint. --locked does not change the outcome; parsing fails first.

Which lockfile version Cargo writes depends on rust-version. In rust-lang/cargo src/resolver/resolve.rs (main at df742db), ResolveVersion::with_rust_version picks V4 for rust-version ≥ 1.83, V3 for ≥ 1.53, and the default when rust-version is unset. I confirmed this with cargo 1.100.0: rust-version 1.76, 1.77, 1.78, and 1.82 produced version = 3; 1.83 and 1.85 produced version = 4. Cargo 1.85.1 with no rust-version also wrote version = 4; cargo 1.78.0 wrote version = 3.

Fix: make the image at least 1.78, ideally the same series as your toolchain file. If you really must build on an older Cargo, set rust-version below 1.83 and regenerate the lockfile so it is written as v3.

Error 2: “feature edition2024 is required”

The lockfile can be fine and a dependency still breaks the old image. A crate with clap = "4" and rust-version = "1.76" (edition 2021), locked by cargo 1.100.0, resolved to clap 4.6.10 and clap_lex 1.1.2. Both list rust_version 1.85 in the crates.io index. On rust:1.76-slim:

error: failed to download replaced source registry `crates-io`

Caused by:
  failed to parse manifest at `/usr/local/cargo/registry/src/index.crates.io-6f17d22bba15001f/clap_lex-1.1.2/Cargo.toml`

Caused by:
  feature `edition2024` is required

  The package requires the Cargo feature called `edition2024`, but that feature is not stabilized in this version of Cargo (1.76.0 (c84b36747 2024-01-18)).
  Consider trying a newer version of Cargo (this may require the nightly release).
  See https://doc.rust-lang.org/nightly/cargo/reference/unstable.html#edition-2024 for more information about the status of this feature.

The same project built on rust:1.85-slim. The rust-version = "1.76" line did not protect the lockfile: with edition 2021 (resolver 2), cargo 1.100.0 still locked the newest versions.

Fix, tested: tell the resolver to respect your rust-version. With .cargo/config.toml

[resolver]
incompatible-rust-versions = "fallback"

regenerating the lockfile on cargo 1.100.0 printed:

     Locking 15 packages to highest Rust 1.76 compatible versions
      Adding clap v4.5.61 (available: v4.6.10, requires Rust 1.85)
      Adding clap_builder v4.5.61 (available: v4.6.10, requires Rust 1.85)
      Adding clap_lex v1.0.1 (available: v1.1.2, requires Rust 1.85)

and the build on rust:1.76-slim then finished with exit 0. The Cargo book (doc/book/src/reference/resolver.md, “Rust version”) documents the fallback setting. The simpler fix is usually to raise the image to the toolchain you actually develop on.

Error 3: your own rust-version is newer than the image

With rust-version = "1.85" in Cargo.toml and rust:1.76-slim, cargo 1.76.0 says:

error: package `demo v0.1.0 (/app)` cannot be built because it requires rustc 1.85 or newer, while the currently active rustc version is 1.76.0

Newer Cargo words it differently. With rust-version = "1.100", both rust:1.85-slim and rust:1.95-slim printed:

error: rustc 1.85.1 is not supported by the following package:
  demo@0.1.0 requires rustc 1.100

(1.95.0 in the second run.) That newer message comes from src/ops/cargo_compile/mod.rs at df742db. When the incompatible package is a dependency rather than your own crate, the same code adds a hint to cargo update <name>@<current-ver> --precise <compatible-ver>.

The opposite trap: rust-toolchain.toml overrides the image

rustup’s overrides documentation (doc/user-guide/src/overrides.md, rust-lang/rustup main at 7747d0c) lists the order: +toolchain on the command line, RUSTUP_TOOLCHAIN, a directory override, the rust-toolchain.toml file, then the default toolchain. The official images just install one toolchain as the default, so a toolchain file in the build context beats the FROM tag.

Same project, rust-toolchain.toml with channel = "1.85", Dockerfile FROM rust:1.76-slim with COPY . .:

#8 0.341 info: downloading component 'rust-docs'
...
#8 10.48 rustc 1.85.1 (4eb161250 2025-03-15)
#8 10.55    Compiling demo v0.1.0 (/app)
#8 10.63     Finished `release` profile [optimized] target(s) in 0.12s

The image’s 1.76 was never used. rustup 1.27.0 downloaded six components, including rust-docs, on every uncached build. On rust:1-slim (rustup 1.29.3, profile minimal in settings.toml) it downloaded three and warned:

info: syncing channel updates for 1.85-x86_64-unknown-linux-gnu
info: latest update on 2025-03-18 for version 1.85.1 (4eb161250 2025-03-15)
info: downloading 3 components
warn: the missing active toolchain `1.85-x86_64-unknown-linux-gnu` has been auto-installed
warn: this might cause rustup commands to take longer time to finish than expected
info: you may opt out with `RUSTUP_AUTO_INSTALL=0` or `rustup set auto-install disable`
rustc 1.85.1 (4eb161250 2025-03-15)

With -e RUSTUP_AUTO_INSTALL=0 the same container fails instead:

error: toolchain '1.85-x86_64-unknown-linux-gnu' is not installed
help: run `rustup toolchain install` to install it

and rustup show active-toolchain says the toolchain file at '/app/rust-toolchain.toml' specifies an uninstalled toolchain. rustup’s CHANGELOG records the history: 1.28.0 (2025-03-04) stopped auto-installing, and 1.28.1 (2025-03-05) “restore[d] the automatic install behavior by default,” with RUSTUP_AUTO_INSTALL=0 as the opt-out.

The switch depends on what you copy. The common cache-friendly Dockerfile copies only Cargo.toml, Cargo.lock, and src. Then the toolchain file is not in the image, the old tag is used, and you get Error 1, 2, or 3 even though the toolchain file says 1.85. That is exactly the drift run in the next section.

The same thing happens in CI

dtolnay/rust-toolchain (main at df2a88e) runs rustup toolchain install … --profile minimal and then rustup default. I ran those two commands for 1.76 in a container next to a channel = "1.85" toolchain file:

info: default toolchain set to 1.76-x86_64-unknown-linux-gnu
...
info: note that the toolchain '1.85-x86_64-unknown-linux-gnu' is currently in use (overridden by '/app/rust-toolchain.toml')
rustc 1.85.1 (4eb161250 2025-03-15)

Outside the project directory, rustc --version was 1.76.0. A workflow that says @1.76 may therefore test 1.85 while your Dockerfile ships 1.76. (This used the action’s commands, not a GitHub-hosted run of the action.)

A checklist

  1. Pick one version and put it in rust-toolchain.toml (channel = "1.85.1" or "1.85", not "stable").
  2. Make every FROM rust:… tag (builder stages too) and every Compose image: rust:… the same major.minor.
  3. Keep rust-version in Cargo.toml at or below that version, and remember it changes the lockfile format at 1.83.
  4. If an older toolchain must build the project, set incompatible-rust-versions = "fallback" and regenerate Cargo.lock.
  5. In Docker, set ENV RUSTUP_AUTO_INSTALL=0 if you would rather fail than download a different toolchain mid-build.

What RuntimeGate catches here, and what it doesn’t

RuntimeGate compares Rust pins from rust-toolchain.toml, a legacy rust-toolchain file, .tool-versions, mise.toml, FROM rust:…, Compose image: rust:…, and dev containers. Rust compatibility is the major.minor series. I ran the RuntimeGate 0.2.1 CLI on seven small test repos.

Drift (rust-toolchain.toml 1.85, FROM rust:1.76-slim with the cache-friendly COPY, Compose rust:1.85-slim), the same layout that hit Error 1 in Docker above:

RuntimeGate checked 3 declarations (node, python, go, rust).

Errors (1):
  [series-mismatch] Rust pins disagree on the major.minor series (1.76 vs 1.85).
exit=1

Legacy file vs .tool-versions (rust-toolchain containing 1.85, .tool-versions rust 1.84.1, builder stage FROM rust:1.85-slim AS build):

RuntimeGate checked 3 declarations (node, python, go, rust).

Errors (1):
  [series-mismatch] Rust pins disagree on the major.minor series (1.84 vs 1.85).
exit=1

Patch only (channel = "1.85.0", FROM rust:1.85.1-slim):

RuntimeGate checked 2 declarations (node, python, go, rust).

Warnings (1):
  [patch-mismatch] Rust pins agree on 1.85 but disagree on patch (Dockerfile#FROM@Dockerfile:1.85.1-slim, rust-toolchain.toml#channel@rust-toolchain.toml:1.85.0).
exit=0

Clean (channel = "1.85.1", FROM rust:1.85.1-slim, Compose rust:1.85.1-slim):

RuntimeGate checked 3 declarations (node, python, go, rust).
OK — declared runtimes agree.
exit=0

Here are the gaps, based on those runs:

  • Cargo.toml rust-version is not read. A repo with only rust-version = "1.85" and FROM rust:1.76-slim printed RuntimeGate checked 1 declaration and OK — declared runtimes agree., exit 0, although that exact pair fails with Error 3.
  • The lockfile version and dependency MSRVs are not checked. RuntimeGate does not read Cargo.lock, the crates.io index, or editions, so Errors 1 and 2 are only caught indirectly, when a toolchain file also disagrees with the image.
  • channel = "stable" is only a warning. With FROM rust:1.76-slim it printed [floating-tag] rust-toolchain.toml#channel in rust-toolchain.toml uses floating tag "stable", which can move. and exited 0.
  • No Rust CI steps. A workflow using dtolnay/rust-toolchain@1.76 next to a 1.85 toolchain file and image passed with 2 declarations. RuntimeGate reads setup-node, setup-python, and setup-go, not Rust actions or rustup commands.
  • No Docker build-context awareness. It does not know whether rust-toolchain.toml is copied into the image or excluded by .dockerignore, or whether RUSTUP_AUTO_INSTALL is set.
  • No Rust end-of-support check. --eol printed [eol-unknown] warnings for each Rust pin (“RuntimeGate does not vendor a Rust end-of-support schedule”).
  • The free RuntimeGate Lite Action (v1, a30a806) checks Node.js only. On the drift repo it printed RuntimeGate checked 0 declarations (node). and No runtime version declarations found. and exited 0.

RuntimeGate catches the common root cause, a toolchain file and a FROM rust: tag on different series. It is not a substitute for reading Cargo’s error. Checkout for the CLI is not live.
