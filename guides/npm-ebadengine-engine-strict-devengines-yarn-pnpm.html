npm WARN EBADENGINE vs “The engine "node" is incompatible”: how npm, Yarn, and pnpm enforce engines

The same package.json can print a warning under npm, fail under Yarn 1, pass silently under Yarn 4, and fail under pnpm only when one setting is in the right file. Whether a wrong Node.js version stops your CI job depends on the package manager, its version, and the field you used.

Every result below was produced on 21 November 2026 by running the package managers against small test projects on Node.js 24.22.1: npm 11.21.1, npm 10.9.0, npm 10.8.2, Yarn 1.22.22, Yarn 4.12.0, and pnpm 12.21.0. The output is quoted as printed. After that comes what actually prevents the error: making the repo’s own version pins agree before anything installs.

The test projects

Two fixtures cover the common cases. In the first, the app’s own engines range excludes the running Node version, and it depends on a local package, old-dep, whose engines also excludes it:

// app/package.json
{
  "name": "app",
  "private": true,
  "engines": { "node": "22" },
  "dependencies": { "old-dep": "file:../dep/old-dep-1.0.0.tgz" }
}

// dep/package.json (packed with npm pack)
{ "name": "old-dep", "version": "1.0.0", "engines": { "node": ">=18 <23" } }

The second uses npm’s newer devEngines field instead of engines:

{
  "name": "app",
  "private": true,
  "scripts": { "build": "node -e \"console.log('built')\"" },
  "devEngines": {
    "runtime": { "name": "node", "version": "^22.12.0", "onFail": "error" }
  }
}

npm: EBADENGINE is a warning unless you turn on engine-strict

With default settings, npm install warned about both the project and the dependency, installed anyway, and exited 0:

$ npm install
npm warn EBADENGINE Unsupported engine {
npm warn EBADENGINE   package: 'app@1.0.0',
npm warn EBADENGINE   required: { node: '22' },
npm warn EBADENGINE   current: { node: 'v24.22.1', npm: '11.21.1' }
npm warn EBADENGINE }
npm warn EBADENGINE Unsupported engine {
npm warn EBADENGINE   package: 'old-dep@1.0.0',
npm warn EBADENGINE   required: { node: '>=18 <23' },
npm warn EBADENGINE   current: { node: 'v24.22.1', npm: '11.21.1' }
npm warn EBADENGINE }

added 1 package in 266ms

npm’s engines documentation says the field is “advisory only” unless the engine-strict config is set, and that it “will only produce warnings when your package is installed as a dependency.” In this test npm 11 also warned about the root project’s own range, so do not read that sentence as “your own engines is never checked.”

With --engine-strict, or engine-strict=true in the project’s .npmrc, the same install failed with exit code 1. npm stops at the first package that does not match. Here that was the app itself; when the app’s own range was changed to >=24, it stopped at old-dep instead:

$ npm install --engine-strict
npm error code EBADENGINE
npm error engine Unsupported engine
npm error engine Not compatible with your version of node/npm: app@1.0.0
npm error notsup Not compatible with your version of node/npm: app@1.0.0
npm error notsup Required: {"node":"22"}
npm error notsup Actual:   {"node":"v24.22.1","npm":"11.21.1"}

npm devEngines: a hard stop, but only on newer npm

npm documents devEngines as a check that runs before install, ci, and run, aimed at people working on the source tree rather than at consumers of a published package. onFail can be warn, error, or ignore, and an unset value behaves like error. With npm 11.21.1, npm install, npm ci, and npm run build all failed with exit code 1, without needing engine-strict:

$ npm run build
npm error code EBADDEVENGINES
npm error EBADDEVENGINES The developer of this package has specified the following through devEngines
npm error EBADDEVENGINES Invalid devEngines.runtime
npm error EBADDEVENGINES Invalid semver version "^22.12.0" does not match "v24.22.1" for "runtime"
npm error EBADDEVENGINES {
npm error EBADDEVENGINES   current: { name: 'node', version: 'v24.22.1' },
npm error EBADDEVENGINES   required: { name: 'node', version: '^22.12.0', onFail: 'error' }
npm error EBADDEVENGINES }

With "onFail": "warn", the same lines were printed as npm warn and the script ran.

The catch is the npm version. npm 10.9.0 failed the install too (its message read Invalid engine "runtime"). npm 10.8.2 ignored devEngines entirely and printed up to date with exit 0. According to the Node.js release index, 10.8.2 is the npm that ships with Node.js 20.20.2, the newest Node 20 release. So if CI is accidentally on Node 20, the field meant to catch the wrong runtime may not run at all. engine-strict still worked on npm 10.8.2: the strict install of the first fixture failed with EBADENGINE.

Yarn 1: the “engine is incompatible” error

Yarn Classic fails the install by default. This is the message developers search for:

$ yarn install
[1/5] Validating package.json...
[2/5] Resolving packages...
[3/5] Fetching packages...
error old-dep@1.0.0: The engine "node" is incompatible with this module. Expected version ">=18 <23". Got "24.22.1"
error Found incompatible module.

The app’s own engines fails it even earlier, at [1/5] Validating package.json... with error app@1.0.0: The engine "node" is incompatible with this module. Expected version "22". Got "24.22.1". Both exited 1. yarn install --ignore-engines (Yarn Classic docs) completed and exited 0. That flag hides the message; it does not make Node 24 a version the dependency supports. Yarn 1.22.22 ignored devEngines: install and yarn run build both succeeded.

Yarn 2+ (Berry): no engines check at all

Yarn 4.12.0 installed both fixtures with exit 0 and printed no engine warning, for either the project or the dependency. It ignored devEngines as well. This is a known difference from Yarn 1. The check was not carried over to modern Yarn (yarnpkg/berry#1177), and maintainers point users to community plugins such as yarn-plugin-engines (not tested here). If a repo moved from Yarn 1 to Yarn 4, its engines field may have quietly stopped protecting anything.

pnpm: engineStrict belongs in pnpm-workspace.yaml

By default pnpm 12.21.0 warned and installed, exit 0:

$ pnpm install
[WARN] Unsupported engine for /tmp/eng/pn: wanted: {"node":"22"} (current: {"node":"24.22.1"})
[WARN] Unsupported engine for old-dep@file:old-dep-1.0.0.tgz: wanted: {"node":">=18 <23"} (current: {"node":"24.22.1"})

Putting engine-strict=true in .npmrc changed nothing. pnpm’s settings page says that only auth, registry, TLS, proxy, and local-address settings are read from .npmrc; everything else goes in pnpm-workspace.yaml. With engineStrict: true there, or with --config.engine-strict=true on the command line, the install failed with exit 1:

$ cat pnpm-workspace.yaml
engineStrict: true
$ pnpm install
Error: ERR_PNPM_UNSUPPORTED_ENGINE

  × Unsupported engine for /tmp/eng/pn: wanted: {"node":"22"} (current:
  │ {"node":"24.22.1"})

The engineStrict docs add that optional dependencies are exempt. They also describe nodeVersion, which makes pnpm check engines against a fixed Node version instead of the one running. pnpm also acts on devEngines.runtime: with "onFail": "error", both pnpm install and pnpm run build exited 1 with ERR_PNPM_BAD_RUNTIME_VERSION, “This project requires Node.js ^22.12.0. Your current Node.js is v24.22.1”. pnpm’s runtimeOnFail setting can override that, and its download mode installs the declared runtime instead of failing.

Summary of what each tool did

  • npm 11.21.1, default: engines mismatch (project or dependency) warns EBADENGINE, exit 0. devEngines.runtime with onFail: error fails install, ci, and run.
  • npm with engine-strict: engines mismatch fails with EBADENGINE, exit 1 (also on npm 10.8.2).
  • npm 10.8.2 (bundled with Node 20.20.2): devEngines ignored.
  • Yarn 1.22.22: engines mismatch fails by default; --ignore-engines bypasses it. devEngines ignored.
  • Yarn 4.12.0: no check for engines or devEngines.
  • pnpm 12.21.0: engines mismatch warns; fails with engineStrict: true in pnpm-workspace.yaml (not .npmrc). devEngines.runtime with onFail: error fails install and run.

Why the error usually shows up in CI or Docker

These checks compare a range with whatever Node happens to be running. They do not ask why it is running. On a laptop that is the version manager’s choice. In CI it is the actions/setup-node input, and in a container it is the FROM tag. When those three are written in different files, they drift. Here is a small repo where the range says 22, CI hardcodes 20, and the Dockerfile moved to 24:

# package.json
"engines": { "node": "^22.12.0" },
"devEngines": {
  "runtime": { "name": "node", "version": "^22.12.0", "onFail": "error" }
}

# .nvmrc
22

# Dockerfile
FROM node:24-slim
RUN npm ci

# .github/workflows/ci.yml (steps)
- uses: actions/checkout@v7
- uses: actions/setup-node@v7
  with:
    node-version: 20
- run: npm ci

The container build’s npm ci runs on Node 24, which fails the devEngines check, as the npm 11 output above shows. The CI job runs on Node 20, whose bundled npm 10.8.2 skips devEngines, and engines only warns. So CI can go green on a version the project says it does not support. The install-time checks are the last line of defense, and here they are inconsistent.

Running the RuntimeGate CLI (0.2.1) on that repo, without installing anything, printed this and exited 1:

$ runtimegate check .
RuntimeGate checked 5 declarations (node, python, go, rust).

Errors (7):
  [major-mismatch] Node.js pins disagree on the major version (20 vs 22 vs 24).
  [range-unsatisfied] actions/setup-node#node-version in .github/workflows/ci.yml (20) cannot satisfy package.json#engines.node "^22.12.0" in package.json.
  [range-unsatisfied] .nvmrc in .nvmrc (22) cannot satisfy package.json#engines.node "^22.12.0" in package.json.
  [range-unsatisfied] Dockerfile#FROM in Dockerfile (24) cannot satisfy package.json#engines.node "^22.12.0" in package.json.
  [range-unsatisfied] actions/setup-node#node-version in .github/workflows/ci.yml (20) cannot satisfy package.json#devEngines.runtime "^22.12.0" in package.json.
  [range-unsatisfied] .nvmrc in .nvmrc (22) cannot satisfy package.json#devEngines.runtime "^22.12.0" in package.json.
  [range-unsatisfied] Dockerfile#FROM in Dockerfile (24) cannot satisfy package.json#devEngines.runtime "^22.12.0" in package.json.

Warnings (1):
  [hardcoded-ci] Node.js CI hardcodes a version (actions/setup-node#node-version@.github/workflows/ci.yml:20) while a version file is present or referenced. Prefer node-version-file / python-version-file / go-version-file so CI cannot drift.

One of those errors is strict on purpose. A version manager given 22 in .nvmrc will install some 22.x release, which may well satisfy ^22.12.0. RuntimeGate can’t know which one, so it treats a major-only .nvmrc as 22.0.0 when checking ranges. It treats a major-only setup-node value as the latest release on that line, because setup-node resolves it that way. The fix is the same either way: pin a version that is inside the range.

The fix: one pin inside the range, read everywhere

Pick a version that satisfies the range, put it in one file, and point CI at that file. Pin the Docker tag to the same version. actions/setup-node documents node-version-file for .nvmrc, .node-version, .tool-versions, mise.toml, and package.json. If both node-version and node-version-file are set, node-version wins (setup-node advanced usage). 22.23.5 was the newest Node 22 release in the Node.js release index on 21 November 2026, and node:22.23.5-slim exists on Docker Hub:

# .nvmrc
22.23.5

# Dockerfile
FROM node:22.23.5-slim
RUN npm ci

# .github/workflows/ci.yml (steps)
- uses: actions/checkout@v7
- uses: actions/setup-node@v7
  with:
    node-version-file: .nvmrc
- run: npm ci

With those three changes, the same check printed this and exited 0:

$ runtimegate check .
RuntimeGate checked 5 declarations (node, python, go, rust).
OK — declared runtimes agree.

Then decide how loud the install-time check should be, based on the package manager you actually use:

  • npm: add engine-strict=true to the project .npmrc if a mismatched engines should fail installs, including your dependencies’ ranges. Use devEngines.runtime for the contributor check, but don’t rely on it where npm older than 10.9 may run.
  • Yarn 1: it already fails. Don’t make --ignore-engines a habit in CI scripts.
  • Yarn 4: nothing checks engines unless you add a plugin, so the pins themselves have to be right.
  • pnpm: set engineStrict: true in pnpm-workspace.yaml, not .npmrc.

What RuntimeGate checks here, and what it doesn’t

  • It reads the repo’s own package.json engines.node, devEngines.runtime (the node entry), and Volta, and checks every Node pin it finds against those ranges: .nvmrc, .node-version, .tool-versions, mise.toml, Dockerfile and Compose images, dev containers, and actions/setup-node.
  • It does not read dependencies’ engines. It skips node_modules, and it does not read lockfiles. In the demo repo, a node_modules/old-dep with "node": ">=18 <21" was present and was not reported. A dependency that drops support for your Node version is still something npm, Yarn 1, or pnpm reports at install time.
  • It does not check engines.npm, engines.pnpm, packageManager, or devEngines.packageManager. It does not run a package manager, and it does not check which Node is installed on the machine. It compares declarations in files.
  • By default, an engines range is compared only to pins in its own package directory, plus root workflows (--engines-scope all compares everything). Node pins are compared by major version, and patch-level differences are warnings.
