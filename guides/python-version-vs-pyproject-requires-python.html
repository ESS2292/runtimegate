Keep .python-version and requires-python in agreement

.python-version is a pin. requires-python in pyproject.toml is a range. GitHub Actions can read either file, and those two modes do not do the same thing.

Python projects often declare a version in more than one place: a .python-version file (used by pyenv, uv, and similar tools), a requires-python field under [project] in pyproject.toml, a FROM python:… line in a Dockerfile, and a python-version or python-version-file input on actions/setup-python. Updating one of those and missing the others is a common way for local installs, CI, and the image to diverge.

A pin and a range are easy to confuse

requires-python is a constraint on which interpreters the project supports, such as >=3.13 or >=3.13.7. It is not, by itself, an instruction to install one exact version. .python-version usually is that instruction: “use 3.13,” or “use 3.13.7.” When the pin is only a major.minor and the range has a patch floor, the two can disagree even if they look similar.

That exact case is still open on the uv tracker. In astral-sh/uv#16012 (opened 24 September 2025), a project had .python-version set to 3.13 and requires-python = ">=3.13.7". uv selected an already-managed 3.13.2 and then failed the constraint. A maintainer wrote that combining the pin and the range automatically would be hard, and recommended putting the patch version in .python-version or omitting the file. The issue was still open when this guide was written on 10 November 2026.

What setup-python actually reads

The official setup-python README says the python-version input is optional. If you omit it, the action tries the default .python-version file; if that file is missing, it uses whatever Python is already on PATH. That PATH version “varies between runners and can be changed unexpectedly,” so the README recommends always setting python-version or python-version-file explicitly.

The advanced usage guide shows both of these:

- uses: actions/setup-python@v5
  with:
    python-version-file: '.python-version'

# or
- uses: actions/setup-python@v5
  with:
    python-version-file: 'pyproject.toml'

Those two inputs are not interchangeable. If both python-version and python-version-file are set, the file is ignored and the hardcoded version wins. And when the file is pyproject.toml, the action resolves a version from requires-python rather than from a pin file. Astral’s guide to using uv in GitHub Actions states the difference directly: python-version-file: ".python-version" uses the project pin; python-version-file: "pyproject.toml" “ignore[s] the pin and use[s] the latest version compatible with the project’s requires-python constraint.”

That pyproject support was requested in actions/setup-python#542 (opened 17 November 2022) so CI would not need a second, duplicated version file. The request was reasonable. The catch is that “latest version that satisfies the range” will move when a new Python release lands, which may or may not be what you want in a production image or a lockstep CI job.

A pattern that stays in agreement

  • Put the version you actually want to run in .python-version. Include the patch if requires-python has a patch floor, as the uv thread recommends.
  • Keep requires-python as the supported range, and make sure the pin satisfies it.
  • In GitHub Actions, set python-version-file: .python-version and do not also set python-version.
  • Pin the Docker image to the same major.minor (or the same patch, if you need it).

If you intentionally test several versions, use a matrix and accept that those extra versions are not the production pin. Matrix entries should still satisfy requires-python.

How to catch drift in CI

The free RuntimeGate Lite GitHub Action checks Node.js pins only, so it will not compare .python-version with requires-python. If the same repository also declares Node.js versions, add Lite for that subset:

- uses: actions/checkout@v5

- name: Check Node.js version pins
  uses: ESS2292/runtimegate-action@v1
  with:
    eol: "true"

The full RuntimeGate CLI also scans Python and Go: version files, requires-python, Dockerfiles, Compose, and setup-python / setup-go steps. It treats Python compatibility as the major.minor series, and it can optionally fail when a pin is past official end of support (Python 3.10 reached end of life on 1 October 2026, per the Python devguide versions table).
